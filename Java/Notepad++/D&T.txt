LocalDate
->represents a date without time zone

class Test {
    public static void main(String[] args) {
    	LocalDate now = LocalDate.now();         //2024-12-31
    	int day = now.getDayOfMonth();
    	int month = now.getMonthValue();
    	int year = now.getYear();
    	
    	LocalDate customDate = LocalDate.of(2024, 12, 01);
		
		LocalDate parsedDate = LocalDate.parse("2024-12-01");
    	
    	LocalDate yesterday = now.minusDays(1);     //2024-12-30 	
    	LocalDate pastDate = now.minusMonths(100);  //2016-08-31
    	
    } 
}

Duration
->represents duration of time between two points in sec/ns

Optional class in Java

Optional<T>

->was introduced to handle null pointer exception in Java
->we can consider it as a box which may or maynot contain a value(diagram)

Usecase: when a method is being called from multiple places and it may or maynot return some value, then make its returnType as Optional

=================================================================================================
Methods:

static<T> Optional<T> ofNullable(T value)

boolean isPresent()
T get()

void ifPresent(Consumer consumer)

T orElse(T value)
T orElseGet(Supplier supplier)

=================================================================================================

class Test {
	
	public static void main(String[] args) {
   
		String str = null;
		
		//previously
		 if(str == null) {
			 System.out.println("null value"); 
		 } else {
		     System.out.println(str.length()); 
		 }

		//method1
		Optional<String> optional = Optional.ofNullable(str);
		
		//method2
		if(optional.isPresent()) {
			System.out.println(optional.get());
		}
		
		//method3
		System.out.println(optional.orElse("hi"));
		
		//method4
		optional.ifPresent(n->System.out.println(n));
	}
}

SOLID principles

S->Single responsiblity
 
  a class should have only one job/reponsibility
  ex: controller class/ Service class
 
O->Open/closed principle
 
  s/w entities 
  
  open for extension 
  closed for modification
  
  How to achieve? Design code using Interfaces & Abstract classes
  
L->Liskov substitution principle
 
   Key idea:
   Subclasses should be able to do everything the parent class can do, without changing the expected behavior
   
class Bird {
    public void fly() {
        System.out.println("Bird is flying");
    }
}

class Sparrow extends Bird {
    // Sparrow inherits the fly method from Bird
}

class Penguin extends Bird {

    @Override
    public void fly() {
        throw new UnsupportedOperationException("Penguins can't fly");            //it violates Liskov principle
    }
}

Correct Approach

interface Flyable {
    void fly();
}

class Bird {
    // Common bird properties and methods
}

class Sparrow extends Bird implements Flyable {
    @Override
    public void fly() {
        System.out.println("Sparrow is flying");
    }
}

class Penguin extends Bird {
    // Penguins do not implement Flyable
}
    
  
I->Interface Segregation principle

Keyidea: client should not be forced to depend on interfaces they do not use 
         it focuses on creating smaller, more specific interfaces rather than one large, general-purpose interface
Example:

Animal interface:    fly(), swim(), walk()
Smaller interface:   Flyable()
	  

D->Dependency Inversion principle
 
KeyIdea:  High-level modules should not depend on low-level modules

ex: Interface create extends jpaRepository
